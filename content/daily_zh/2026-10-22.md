## 1. OpenAI 把 GPT-6 与 Codex 放进 Google Cloud 的 Model Garden

### 发生了什么

10 月 21 日，OpenAI 与 Google Cloud 宣布 GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna 以及 OpenAI 的 Codex 智能体编码工作流以私有预览形式进入 Google Cloud 的 Model Garden，首批面向选定企业客户，全面可用称将在数周内到来。客户通过 Google Cloud Marketplace 采购，可直接消耗已有的云承诺额度；推理跑在专用 Google Cloud 基础设施上，请求经隔离网关转发，提示词与输出不出客户数据边界、也不用于训练。Codex CLI 与 Desktop 已可把推理指向该平台，Gemini for business 与 Google Antigravity 内的接入被列为即将推出。零数据保留与机密计算在首发时尚未提供。

### 为什么重要

本周卡住的是渠道，不是能力。微软独占授权到期后 AWS 于 4 月开始托管，如今三大美国云都上架了 OpenAI 的模型，而 Google 干脆把自己宣传成唯一同时提供 Gemini、Claude 与 GPT 的大厂云。这把模型选择从「新开一家供应商」变成「现有云合同里的一个条目」，也让 Gemini 必须在最强对手摆在旁边的货架上赢下企业负载。对采购方而言，实际收益是议价空间与单张账单；对 OpenAI 而言，则是在不自建渠道的前提下换触达。

### 核心技术点

- 私有预览：10 月 21 日起 Model Garden 内提供 GPT-6 Astra、GPT-6.1 Sol、GPT-6 Luna 与 Codex 工作流
- 经 Google Cloud Marketplace 采购，可消耗既有承诺额度，账单合并为一张
- 推理跑在专用 Google Cloud 基础设施、经加固的隔离网关；提示与输出留在客户边界内，不用于训练
- 零数据保留与机密计算列为即将推出，首发不可用
- Codex CLI 与 Desktop 已可把推理指向该平台，Gemini for business 与 Antigravity 集成待上线
- Google 称自己是唯一同时上架三家头部闭源模型的大厂云：Gemini 4 Argon、Claude Fable 5.1、GPT-6 Astra
- OpenAI 表示微软仍是其首要云伙伴

## 2. Recursive 开源 Flint：由自家研究机器造出的 39.8B/2.5B 编码 MoE

### 发生了什么

10 月 21 日，Richard Socher 领衔的 Recursive Superintelligence 发布首个模型 Flint：39.8B 总参、每 token 约 2.5B 激活的编码 MoE，256 个路由专家中选 6 个再加 1 个共享专家，模型卡配置的上下文为 262,144 token。权重以 Apache 2.0 放在 Hugging Face，量化后最小 11.4 GB，官方称在 M4 Pro 笔记本上超过 125 token/s、在 64GB 的 NVIDIA RTX Spark 短上下文下超过 150 token/s。厂商自报成绩为 SWE-bench Pro v2 89.7%、SWE-bench Verified 74.2%、Terminal-Bench 2.1 54.9%。Recursive 称该模型从零开始不到四个月建成，其自动化研究系统 Eureka Machine 参与了包括架构、量化与 kernel 在内的几乎每一层。

### 为什么重要

要分开看两件事。小的一件是它确实是个能打的本地编码模型：约 6% 的激活比换来笔记本级速度，而这样的质量平时只在集群级系统上被报告。大的一件是作者是谁。如果一套自动化研究系统真的在小团队、四个月的时间尺度上参与了架构、量化和 kernel 的设计，那竞争瓶颈就从人头与算力，转移到研究回路本身的吞吐量，而所有实验室现在都在测同一件事。这里需要独立复现，因为 SWE-bench Pro v2 的 89.7% 高于同一模型在 SWE-bench Verified 上的分数，这个反差值得再看一眼。

### 核心技术点

- 总参 39.8B、每 token 约 2.5B 激活（约 6%），256 个路由专家选 6 加 1 个共享专家
- 模型卡配置上下文 262,144 token；博客提到最高 512K，但 256K 内效果最佳
- Apache 2.0 权重在 Hugging Face，量化后最小 11.4 GB
- 厂商自报：SWE-bench Pro v2 89.7%、SWE-bench Verified 74.2%、Terminal-Bench 2.1 54.9%
- M4 Pro 笔记本 125+ token/s，64GB RTX Spark 短上下文 150+ token/s
- Eureka Machine 自动化研究系统参与架构、量化与 kernel；不到四个月从零建成
- 首日即支持 llama.cpp、Ollama、LM Studio、vLLM、SGLang 与开源 rec 引擎，可在 OpenCode 与 Pi 免费试用

## 3. llm-d 1.0 在 CNCF 下发布：面向智能体集群的缓存感知路由

### 发生了什么

llm-d 项目 10 月 20 日在 PyTorch Conference 北美站发布 1.0，到 10 月 21 日成为 AI 基础设施圈的主要议题。该项目 2025 年由 Red Hat、IBM、Google Cloud、CoreWeave 与 NVIDIA 共同发起，现为 CNCF Sandbox 项目，作用是把一群 vLLM 与 SGLang 服务器在 Kubernetes 上编成一个统一的推理池。1.0 引入缓存感知路由（跟踪哪个副本已持有某智能体的前缀）、带流量优先级的多租户 QoS、零停机升级与稳定 API。贡献方给出的数据是混合服务成本约每百万 token 0.11 美元、上下文重的智能体负载成本降 5 到 10 倍、输出吞吐 3 倍，最多可无抢占地支撑 3,000 个并发编码智能体。在 Ironwood TPU 上，前缀感知路由配合主机内存卸载把首 token 中位时延砍掉 85% 以上、吞吐提升 2.4 倍。Google Cloud 正在把它集成进 GKE，覆盖 TPU 与 NVIDIA GPU。

### 为什么重要

智能体负载打破了「一次请求即结束」的假设：一个智能体的多次调用共享长前缀、成簇到达，并且在工具循环中途不能被抢占。llm-d 1.0 是第一个硬化版开源发布，把前缀局部性与抢占策略当成调度的一等输入，而不是调参旋钮。商业含义很直接：如果中立、由 CNCF 治理的推理池能以每百万 token 0.11 美元的混合成本支撑 3,000 个并发智能体，那专有推理优化本身的利润空间会被压缩，差异化会退回到模型质量与垂直整合。

### 核心技术点

- 2025 年由 Red Hat、IBM、Google Cloud、CoreWeave、NVIDIA 发起，现为 CNCF Sandbox，25 家以上组织、500 余名贡献者
- 缓存感知路由把智能体下一次调用送到已持有其前缀的副本
- 带流量优先级的多租户 QoS、零停机升级、稳定 API
- 混合服务成本约每百万 token 0.11 美元；上下文重负载成本降 5 至 10 倍；输出吞吐 3 倍
- 可无抢占支撑最多 3,000 个并发编码智能体
- Ironwood TPU 结果：前缀感知路由加主机内存卸载，首 token 中位时延降 85% 以上、吞吐提升 2.4 倍
- Google Cloud 正把 llm-d 1.0 集成进 GKE，覆盖 TPU 与 NVIDIA GPU；IBM Research 称比全专有配置推理成本低 11.5 倍

## 4. NVIDIA 把手机基站变成算力：T-Mobile 打通首通现网 AI-RAN 通话

### 发生了什么

10 月 21 日在 GTC 柏林，NVIDIA 与 Nokia 表示运营商正在把加速计算装入中心机房、城域站点与单个基站，让电信网络本身成为分布式 AI 算力。T-Mobile 在现网打通全球首通 AI-RAN 通话，跑的是 Nokia anyRAN 软件加 NVIDIA Aerial RAN Computer；BT、德国电信、Elisa 与 Orange 排队试点，其中 Elisa 已完成欧洲首个 AI-RAN 外场试验，BT 正在准备英国现网试点。全球已有近 20 家运营商宣布在该栈上开展 AI-RAN 合作，商用服务目标定在 2027 年。同日 NVIDIA 推出 DSX MaxLPS，称同等 token 产出下最多省电 30%，并给出面向欧洲 AI 工厂的 DSX POD 参考设计，冷却用水最高可减至零。Nscale 在冰岛的测试显示，同样 264 千瓦预算下推理吞吐高出 49%。

### 为什么重要

这轮 AI 建设卡在土地、电力与并网上，而不是 GPU。复用运营商的站址与光纤，可以把算力搬到离用户更近的地方，把一项沉没的国家级资产变成推理足迹，这与再建一座新园区是本质不同的解法。它同时重写了电信生意：已经握着铁塔、供电与回传的运营商，可以卖时延而不是卖带宽。难点在调度，因为无线流量不可让路、AI 任务必须随时退让，这正是 MaxLPS 与柔性用电那套东西要解决的。

### 核心技术点

- T-Mobile 用 Nokia anyRAN 跑在 NVIDIA Aerial RAN Computer 上，在现网打通全球首通 AI-RAN 通话
- BT、德国电信、Elisa、Orange 试点；Elisa 完成欧洲首个 AI-RAN 外场试验；近 20 家运营商宣布合作
- 算力分三层部署：中心机房、城域站点、单个基站
- 以 GPU 加速替代固定功能无线芯片，让 AI 负载与射频信号处理同机运行
- DSX MaxLPS 称同等 token 产出省电 30%；Nscale 冰岛测试同样 264 千瓦预算下吞吐高 49%
- 面向欧洲 AI 工厂的 DSX POD 参考设计，冷却用水最高可减至零
- AI-RAN 商用服务目标 2027 年

## 5. LiteLLM 1.107.0 从自家发布流水线带出凭据窃取器

### 发生了什么

10 月 21 日，每周被下载数千万次的 LLM 网关库 LiteLLM 的 1.107.0 版本带着恶意代码发布到了 PyPI 与项目 Docker 标签。覆盖 Linux、macOS、Windows 的全部七个 wheel 把 cook.pth、cook.py、sitecustomize.py 三个文件塞进 site-packages；两个载荷会在任一 Python 进程启动时执行，哪怕该进程从未 import litellm。窃取器会收集 SSH 密钥、云凭据、CI/CD 机密、浏览器密码、shell 历史、AI 工具 token 与 LiteLLM 代理的上游密钥，并外发到 www.litellm[.]dev；同时另一段守护进程每小时轮询一个托管在 GitHub 的域文件，执行其返回的任意代码。上游 GitHub 源码不含这些文件，PyPI 已下架 1.107.0，1.106.2 与 1.107.0 的两个候选版是干净的。SafeDep 以中等偏高置信度判断，是 BerriAI 自家的私有发布流水线用被篡改的 git 源构建出了这些 wheel，并指出该版本没有来源证明、也没有对应的公开 GitHub Actions 记录。

### 为什么重要

这是 LiteLLM 今年第二次供应链事故，而值得注意的正是载体：发布出去的产物与可审计的源码不一致，所以常规的依赖审查会直接放行。LiteLLM 恰好是把各家模型 API 密钥集中存放的那个组件，价值高于通用包，这也解释了为什么载荷专门去找 AI 工具的凭据。对团队来说，实操结论是别再把模型网关当普通依赖：固定版本、在有来源证明时校验它、并假定所有跑过该版本的主机上能被读到的每一个密钥都已泄露。

### 核心技术点

- 2026 年 10 月 21 日 11:39:51 至 11:40:13 UTC 之间，七个 wheel（Linux、macOS、Windows）发布到 PyPI
- 在 site-packages 植入 cook.pth、cook.py、sitecustomize.py；载荷在 Python 启动时执行，无需 import litellm
- 外发目标 www.litellm[.]dev；窃取 SSH 密钥、云凭据、CI/CD 机密、浏览器密码、shell 历史、AI 工具 token 与代理上游密钥
- 后门守护进程每小时轮询 GitHub 上托管的域文件并执行返回代码
- Docker 标签 v1.107.0、latest、main-latest、main-stable 同样受影响
- 上游 GitHub 源码干净；PyPI 已下架 1.107.0；1.106.2 与两个 1.107.0 候选版安全
- 无 CVE 编号；受影响版本无来源证明；为 2026 年 3 月之后 LiteLLM 第二起供应链事故

# 今日重要论文

## The Virtual Biotech: a Multi-Agent AI Framework for Therapeutic Discovery and Development

该研究 10 月 21 日发表于 Science（2 月先以 bioRxiv 预印本形式发布），是斯坦福提出的框架：一个首席科学官智能体向遗传学、组学、化学信息学与临床数据等方向的专职科学家智能体派活，再由一个审阅智能体复核。在一次展示中，37,075 个临床研究员智能体在六小时内整理了 55,984 项 II、III 期试验的结局数据，作者估算若由单个智能体完成需 76.6 天；智能体标注与人类审阅者在主要终点上的一致率为 89.7%。案例研究提出了针对肺癌的 B7-H3 抗体偶联药物策略，并指出一项已终止的溃疡性结肠炎试验的失效模式。作者强调单个错误可能在系统中级联传播、人类专家参与仍不可缺；这些是智能体整理的观察性关联，不构成湿实验证据。

## google-research/harness2

Harness² 是 Google Research 面向「开放世界中的递归式智能体 harness」的开源框架，10 月初以 Apache 2.0 发布，并配有 arXiv 论文（2610.14224）。它把 harness 本身——提示词、工具、记忆、技能与编排——当成研究对象而不是实现细节，并提供可跑通的基准路径：用 uv 安装、初始化 JobBench，再以 k=1 并行跑一轮。仓库现有 17,184 星与 1,594 个 fork，一周内增加约 1.6 万星，10 月 21 日位列 GitHub Python 趋势榜首，对研究代码来说速度相当罕见。它说明 harness 的可移植性与可评测性正在变成共享词汇，而这距 Google 自己的智能体安全工作只隔一周，距另两家实验室放出 harness 无关工具只隔五天。

链接：https://github.com/google-research/harness2

# 趋势观察

今天五条里有三条都在争同一层：模型与负载之间的那一层。Google 把 OpenAI 的模型搬上自家货架、llm-d 把推理池硬化、NVIDIA 把算力推进基站，都是想握住「请求在哪被路由」而不是「谁来回答」。LiteLLM 事件是同一层从另一侧露出的样子：正因为它把各家厂商的密钥集中在一个进程里，才值得一年被攻击两次。这个模式与过去两周的走向一致：能力在被商品化，而路由、缓存局部性、电力预算与来源证明，正在成为稀缺、可防御、也可被攻击的资产。
