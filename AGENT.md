# AI Daily Frontend — Frontend Implementation Specification

You are a senior frontend engineer and product UI engineer.

Build the frontend for an existing repository named **AI Daily**.

This is NOT a traditional news website.

It is a **personal AI news archive and reading tool** whose content is generated by an existing AI news-generation Skill. Every day, the Skill researches frontier AI developments, produces a five-story Markdown digest in English and Simplified Chinese, and stores the resulting documents in the repository.

Your job is to build the frontend experience on top of that existing content system.

---

# 1. Product Definition

## Product Type

AI Daily is:

* a personal AI news archive;
* a chronological archive of daily AI research and industry developments;
* a lightweight research / reading tool;
* a custom Markdown reader;
* a visually distinctive scroll-based archive.

It is NOT:

* a traditional news portal;
* a magazine homepage with large images;
* a dashboard;
* a social feed;
* a glassmorphism UI;
* a card-heavy SaaS dashboard;
* a cyberpunk interface.

The product should feel like:

> a dark technical archive with editorial typography and tactile document cards.

Core design keywords:

* dark
* technical
* editorial
* quiet
* precise
* dense
* tactile
* minimal
* chronological

The README is not an application data source.

The repository boundary is:

```
Content Domain
    ↓
./content/

Application Domain
    ↓
./frontend/
```

# 2. Repository and Existing Content Contract

Before writing code:

1. Inspect the existing repository.
2. Identify the existing frontend framework and build system.
3. Reuse the existing project structure and conventions whenever practical.
4. Do NOT replace the framework unless the repository is obviously broken or incomplete.
5. Do NOT modify the existing AI news-generation Skill, templates, state files, or content-generation pipeline unless explicitly required for frontend compatibility.
6. Do NOT introduce a backend or database.
7. Treat the `./content/` directory as the canonical content domain.
8. Treat the content domain as read-only from the frontend application's perspective.

The repository separates content generation from frontend code.

# 3. Daily Index Contract

The frontend MUST support `./content/data/daily-index.json` version 1.

The daily index is the primary machine-readable archive index for the frontend.

Expected structure:

```json
{
  "version": 1,
  "generated_at": "2026-09-22T20:00:00Z",
  "entries": [
    {
      "date": "2026-09-22",
      "title": "AI Daily Digest - 2026-09-22",
      "summary": {
        "en": "Today's major developments...",
        "zh": "今日的主要进展…"
      },
      "categories": [
        "Models",
        "Research",
        "Agents"
      ],
      "tags": [
        "OpenAI",
        "LLM",
        "Agents"
      ],
      "news_count": 5,
      "documents": {
        "en": "./content/daily/2026-09-22.md",
        "zh": "./content/daily_zh/2026-09-22.md"
      },
      "news": [
        {
          "index": 1,
          "title": "Example Model Release",
          "summary": "A concise story summary.",
          "category": "Models",
          "tags": [
            "LLM",
            "Reasoning"
          ]
        }
      ]
    }
  ]
}
```

The daily `summary` is a localized object: `{ "en": ..., "zh": ... }`. The frontend resolves it against the current UI language and falls back to the other language when one side is missing. Legacy indexes where `summary` is a plain string MUST still be readable — treat the string as the English summary.

The frontend MUST NOT hardcode daily entries.

The frontend MUST NOT scan the entire repository to discover daily files when `daily-index.json` is available.

Use `daily-index.json` as the authoritative archive index.

The frontend should have a dedicated data-access layer responsible for:

* loading the index;
* validating or safely narrowing the schema;
* finding a daily entry;
* searching entries;
* filtering by category;
* filtering by tag;
* resolving English/Chinese Markdown paths.

The frontend MUST treat document paths in the index as content-domain paths and resolve them relative to the repository root.

Do not assume the current working directory is `./content/`.

# 4. Markdown Contract

Daily Markdown documents are stored under:

```text
./content/daily/
./content/daily_zh/
```

English daily documents follow:

```text
./content/daily/YYYY-MM-DD.md
```

Chinese daily documents follow:

```text
./content/daily_zh/YYYY-MM-DD.md
```

The frontend MUST resolve the document paths from `daily-index.json` instead of constructing paths independently whenever possible.

English:

```yaml
---
date: YYYY-MM-DD
language: en
title: AI Daily Digest - YYYY-MM-DD
summary: ...
categories:
  - ...
tags:
  - ...
news_count: 5
---
```

Chinese:

```yaml
---
date: YYYY-MM-DD
language: zh_CN
title: AI 每日简报 - YYYY-MM-DD
summary: ...
categories:
  - ...
tags:
  - ...
news_count: 5
---
```

Each daily document contains exactly five major news items.

Each news item contains:

```text
Title
What Happened
Why It Matters
Key Technical Points
Links
Category
Tags
```

The category and tags are represented in the Links section as:

```markdown
- Category: Models
- Tags: LLM, Reasoning, OpenAI
```

The frontend MUST parse and display this structure cleanly.

Do not require the Markdown to be written specifically for the frontend.

The Markdown remains a human-readable canonical document.

# 9. Scroll Interaction

Use:

> **Natural scrolling + gentle snap**

Do NOT make the page feel like a hard presentation or slideshow.

Scrolling should remain natural.

However, when the user slows down or releases the scroll, cards may softly settle toward the closest visual position.

Avoid aggressive full-page snapping.

The implementation should feel closer to:

```text
natural scroll
+
soft positional guidance
```

than:

```text
one wheel event = exactly one page
```

---

# 10. Scroll-Driven Card Motion

Card motion must be driven by scroll position.

Do NOT implement the effect as independent "play animation once" events.

Card visual state should depend continuously on its position relative to the viewport.

At minimum, use:

```text
translateY
scale
opacity
z-index
```

Conceptual states:

### Current card

```text
scale: ~1
opacity: ~1
```

### Entering card

```text
scale: slightly smaller → 1
opacity: lower → 1
translateY → center
```

### Leaving card

```text
scale: 1 → slightly smaller
opacity: 1 → lower
translateY → top / outside focus region
```

Cards should visually move according to scroll direction.

The user should feel:

> time is moving through the archive.

Do not overdo depth or perspective.

Avoid 3D card rotation.

Avoid excessive parallax.


The fixed date indicator and card date serve different purposes:

* card date = content identity;

# 24. Search

Search must operate across the `daily-index.json` metadata.

Searchable fields:

Daily level:

* date;
* title;
* summary (both `en` and `zh`);
* categories;
* tags.

News level:

* news title;
* news summary;
* category;
* tags.

Search results should identify:

* date;
* matching news title when applicable;
* relevant category/tag;
* concise context.

Example:

```text

  02  New Agent Framework

20 SEP 2026
  03  ...
```

Clicking a news-level result should navigate to:

```text

```

Search should feel like a tool surface rather than a large standalone marketing page.

```text
English
```


# 32. Markdown Rendering Requirements

## Content Loading Architecture

The frontend should follow this content-loading sequence:

```text
./content/data/daily-index.json
        ↓
DailyEntry
        ↓
entry.documents.en / entry.documents.zh
        ↓
Markdown document
        ↓
Markdown parser
        ↓
Custom Markdown Reader
```

The archive interface should use `daily-index.json` metadata only.

The full Markdown document should be loaded when the user enters a Daily Reader, rather than loading every historical Markdown document during initial application startup.

The frontend must not treat Markdown files as the primary archive-discovery mechanism.

The reader must correctly render:

* headings;
* paragraphs;
* lists;
* links;
* code blocks;
* inline code;
* tables if present;
* separators;
* emphasis;
* metadata;
* external links.

Handle empty optional links gracefully.

For example, if Paper or GitHub does not exist for a news item:

* do not render a broken link;
* do not render an empty button;
* hide the unavailable link cleanly.

The Markdown parser should not visibly expose YAML front matter in the document body.

1. scroll-driven layered archive cards;
2. subtle hover expansion / information reveal;
3. card-to-reader transition;
4. right-side contents opacity transition;

Do NOT add animation simply for decoration.

Avoid:

* bouncing;
* spinning;
* elastic UI everywhere;
* excessive page-load choreography;
* giant entrance animations;
* continuous floating elements.

Future animations may be added only where they improve:

* information hierarchy;
* orientation;
* continuity;
* interaction feedback.

Respect:

```css
prefers-reduced-motion
```

Provide a reduced-motion mode that disables or simplifies non-essential motion.

# 44. Performance

The archive may contain hundreds or thousands of daily entries.

Do not assume only a few entries exist.

Design the archive so it remains performant for long histories.

Avoid rendering unnecessarily complex DOM structures for every historical card.

Use virtualization or progressive rendering if actually needed.

Do not optimize prematurely if normal rendering is sufficient.

Markdown documents should be loaded on demand rather than all at application startup.

# 52. Content Domain Isolation

The `./content/` directory belongs to the AI news-generation pipeline.

The frontend agent MUST treat it as an external read-only content source.

Do NOT:

* rewrite `SKILL.md`;
* rewrite `TEMPLATE.md`;
* rewrite `TEMPLATE_zh.md`;
* modify `state/`;
* modify `config/`;
* regenerate daily Markdown;
* modify `daily-index.json` as part of normal frontend runtime;
* introduce a database to mirror the content.

Frontend development must remain isolated from content generation.

If a content-contract inconsistency is discovered, report it clearly rather than silently modifying the content-generation system.
